# EDMS 결재본 서식 (E-HLF-32) — 모든 PQR 의 바탕

담당자 지시(2026-09-03): **"앞으로 작성하는 모든 PQR 은 이 양식을 참고해서 작성한다."**
그러므로 보고서의 서식은 언제나 EDMS 결재본 서식이고, 전년도 결재본(HLF-QC-126-01 양식,
표지·결재표·개정 내역이 있는 것)은 **값과 문안의 근거**로만 쓴다. 담당자가 실제로 하는 일도
같다 — EDMS 서식을 제품에 맞게 손본 뒤(항 나누기·표 늘리기), 값만 갈아 끼운다.

## 알아보는 법
- 바닥글에 `EHLF-32/Rev.000` 이 있다(전년도 결재본은 `한림제약 HLF-QC-126-01/Rev.010-1`).
  엔진(`pqr/engine/edms.py`)은 파일 이름이 아니라 이 바닥글로 서식을 알아본다.
- 머리글 표는 세 줄뿐 — `문서번호` / `Rev. No.` / `Page n / N`. **문서번호·Rev. No. 는
  비워 둔다**(EDMS 가 결재 때 매긴다). 작성일자·제품명 줄이 없으므로 머리글 칸을 **위치로
  짚으면 안 된다** — 세 번째 줄은 쪽 번호 필드다(라벨로 찾을 것).
- 표지·'검토 및 승인' 결재표·개정 내역이 **없다**. 첫 쪽은 바로 목차 표(항 이름 + 쪽수).
  서명란도 없다 — 결재는 EDMS 에서 한다.
- 파일을 두는 곳: 제품 폴더(또는 그 안의 `16. 전년도 PQR` 폴더), 없으면 입력 폴더의 `공통/`.
  이름에 `완성본`·`제출` 이 든 파일은 결과물이므로 서식으로 보지 않는다.

**표는 한 줄짜리 뼈대**(연번 1 행 하나)다. Lot 수만큼 행을 복제하고, 제품에 항이 더 필요하면
담당자가 항을 나눈다 — 퀴노비드안연고(내수·수출) 결재본은 같은 서식에서 6.1/6.2, 7.1/7.2,
9.2.1.x/9.2.2.x, 13.1.1/13.1.2, 13.3.1/13.3.2 로 갈라 표 49개가 됐다.
**엔진은 있는 표를 채우지 표를 새로 만들지 않는다.** 그래서 '보고서 작성' 은 이렇게 돈다
(`pqr/engine/writer.py`):

1. **전년도 결재본**(평가항목 16 — .doc/.docx, 또는 .zip 안의 것)을 바탕으로 본문을 채운다.
   제품마다 다른 항·표 구조와 문안이 거기 있다. 압축 안의 .doc 도 꺼내 변환한다(디겐타안연고가
   압축만 있어 요약본이 나온 일이 있다). Cpk 첨부 엑셀도 같은 압축에서 물려받는다.
2. **EDMS 서식이 있으면 채운 본문을 서식 껍데기에 옮겨 담는다**(`pqr/engine/rehouse.py`):
   표지·'검토 및 승인' 결재표·개정 내역·옛 목차를 버리고, 서식의 목차(제목 + 목차 표)를 맨 앞에,
   머리글·바닥글(로고·문서번호·Rev. No.·Page·EHLF-32/Rev.000)과 쪽 설정을 서식 것으로. 1항 제목은
   '앞에서 쪽 나눔'. 패키지는 채운 문서 쪽(스타일·번호·그림이 본문에 필요)이고 서식 부품만 새
   이름(`edms_header1.xml` …)으로 붙인다. 목차 쪽수는 그다음 `link_toc` 가 PAGEREF 로 잇는다.
3. 서식이 없으면 전년도 양식 그대로 만들고 문의 목록에 "서식을 두세요" 를 남긴다.
   전년도 결재본이 없는 첫해 제품은 서식을 바탕으로 직접 채운다(표 구조는 서식 그대로라 값이
   덜 찬다 — 담당자가 서식을 제품에 맞게 손본 EDMS 결재본을 넣는 편이 낫다).

서식은 **프로그램에 껍데기가 들어 있다**(`pqr/data/edms_shell.docx` — 목차·머리글·바닥글·쪽
설정만 있고 본문·제품 고유 글은 없다). 그래서 담당자는 아무것도 두지 않아도 '보고서 작성' 이
EDMS 양식으로 나온다. 서식이 개정되면 새 서식(.docx)을 **입력 폴더의 `공통/`** 에 두면 그것이
먼저 쓰인다(제품 폴더 것이 있으면 그것이 더 먼저). 이름은 상관없고 바닥글의 `EHLF-32` 로 알아본다.

담당자 PC 는 표준 파이썬뿐이라(pywin32 없음) 옛 워드(.doc) 변환은 `convert.py` 가 Word 를
**PowerShell COM** 으로 부른다(win32com 이 없을 때). Cpk 엑셀 채우기(`xls_fill`)의 Excel 백엔드는
아직 win32com 이 필요해, 없으면 그래프 없이 값만 채운 .xlsx 로 떨어지고 문의 목록에 남는다.

## 채울 때 지킬 것 (2026 퀴노비드 결재본에서 확정)
- **서식은 그대로, 값만 갈아 끼운다.** 서식 글(1항·2항 목적·배경, 5항, Cpk 판정표, 14·15항
  특이사항 문안)은 손대지 않는다. 표의 열 수·머리행·병합도 서식대로.
- 값이 없는 칸은 `N/A` 를 적지 말고 **사선**(셀 테두리 `w:tr2bl`, `val="single"`). 서식에
  들어 있는 `N/A`(10.x 비고, 12항 비고, 14.2 특이사항)도 표 안이면 사선으로 바꾼다.
  `해당사항 없음`·`해당 없음` 은 내용이므로 그대로 둔다.
- **요약 블록에서 열을 가로로 합치지 않는다.** 정성 항목 열은 열마다 세로 병합 + 사선 하나.
  나중에 값을 넣게 되면 세로 병합과 사선을 먼저 푼다(입자도 Cpk 건).
- 16.1 표에는 **Cpk 1 미만 항목을 빠짐없이** 적고 9.2 세부표의 Cpk 칸과 맞춘다.
- **평가 년도 생산 Lot 이 10 미만이면 Cpk 를 산출하지 않는다 — 모든 PQR 공통**(담당자 2026-09-04).
  기준은 설정 `thresholds.cpk_min_lots` 한 곳에 두고(`pqr/engine/qc.py`), 9항 요약 행(Cpk·판정은
  사선), 16항 문안("… n Lot 으로 10 Lot 미만이므로 QC-126 에 따라 Cpk 를 산출하지 않았음"),
  첨부 Cpk 계산 파일(만들지 않고 문의 목록에 남김), 대시보드 판정이 모두 이것을 따른다.
  퀴노비드 수출용(2 Lot)이 이 경우다.
- **다른 제품의 결재본·규격을 쓰지 않는다.** 전년도 결재본에 그 제품의 이름(또는 코드)이 없으면
  엔진이 멈추고 이유를 말한다(`writer.other_product`) — 퀴노비드 결재본으로 디겐타안연고를 쓰는
  일을 막는다. Cpk 한계(입자도 상한·함량 상하한·금속성이물 상한)와 13.3 관리 규격은 **그 제품의
  9.1 허용기준 글에서 읽는다**(`recipe_ointment.parse_limits`). 못 읽으면 기본값(퀴노비드)으로
  계산하고 문의 목록에 "확인 필요" 를 남긴다. 성적서의 함량 규격도 글에서 읽는다(90.0~110.0 고정 아님).
- 자릿수는 원자료를 따른다(입자도 정수 → 평균도 정수, 함량 소수 1자리, Cpk 소수 2자리).
- 목차 쪽수는 실제 쪽과 맞춘다(2026 퀴노비드: 4→4, 7→5, 9→10, 13→27, 15~18→32).
- **빈 쪽을 만들지 않는다.** 서식은 `빈 문단 + (빈 문단 + 하드 쪽나눔)` 이 반복돼, Word 가
  LibreOffice 보다 쪽을 더 쓰면(32 → 37) 빈 문단이 다음 쪽으로 밀려 빈 쪽이 생긴다.
  `docedit.tidy_page_breaks()` — 쪽나눔 앞 빈 문단 삭제, 빈 문단+하드 쪽나눔 → 다음 문단의
  '앞에서 쪽 나눔', 문서 끝 빈 문단 삭제(표 바로 뒤는 남김).
- **칸 폭은 그리드대로, 표 배치는 '고정'.** 서식의 칸 폭 값은 단위가 뒤섞여 Word 가 자동 맞춤에서
  열을 엉뚱하게 나눈다(생균수가 두 줄, 튜브인쇄가 네 줄). `docedit.fix_all_table_widths()` 로
  맞추면 결과는 되도록 한 줄, 긴 문장(튜브인쇄·압인상태)은 두 줄이 된다 — 담당자가 원한 모양.
- **Word 가 "일부 콘텐츠를 읽을 수 없습니다" 로 복구를 묻게 하지 않는다.** 가장 흔한 원인은
  **이름이 같은 스타일이 둘**인 것 — 한글 Word 서식의 `a`(이름 Normal)를 LibreOffice 가 변환한
  결재본(이미 `Normal` 이 있다)에 그냥 보태면 이름이 겹친다(2026-09-04 담당자 PC 에서 실제로
  생김). `rehouse._merge_styles` 는 이름이 같으면 보태지 않고 기존 스타일로 **연결**하고,
  styleId 만 겹치면 `edms_…` 로 바꿔 넣으며, 보태는 스타일에서 `w:default` 를 뗀다(기본 스타일은
  종류마다 하나). 저장 뒤 `rehouse.check_styles()` 로 이름·id 중복과 기본 스타일 둘을 다시 보고,
  걸리면 보고서를 내보내지 않는다. **XSD 검증과 LibreOffice 변환은 이 문제를 못 잡는다** — 둘 다
  통과하고도 Word 만 거부하므로, 스타일 검사를 따로 둔 것이다.
- **`settings.xml` 같은 부품도 자식 차례가 스키마로 정해져 있다.** `updateFields`(목차 쪽수를
  Word 가 다시 계산하게 하는 표시)를 `</w:settings>` 앞에 그냥 붙이면 `compat`·`rsids` 뒤에
  놓여 스키마 위반이 되고, Word 는 문서를 열지 못한다(2026-09-04 디겐타안연고에서 실제로 생김).
  `polish.set_update_fields()` 가 `ooxml_order.SETTINGS` 차례대로 제자리에 넣는다.
- **옛 워드(.doc)를 `zipfile` 로 열지 마라.** `.doc` 는 OLE 파일(머리 `D0CF11E0`)인데 꼬리에
  테마(.thmx) zip 이 박혀 있어 파이썬 `zipfile` 이 그것을 열어 준다. 부품은
  `theme/theme/theme1.xml` 뿐이고 `word/document.xml` 은 없다. 이걸 복제해 '제출용' 으로 내놓아
  2.9 KB 짜리 파일이 나왔고 Word 가 거부했다(2026-09-04 디겐타안연고 — 담당자가 파일을 보내 줘서
  잡았다). `prior_report.is_docx()` 로 **`word/document.xml` 이 있는지** 보고 없으면 쓰지 않는다.
- **내보내기 전에 `verify.check_docx()` 를 통과해야 한다** — 부품 형식 등록, 관계가 가리키는
  부품, 스타일 이름·id 중복, 스키마가 정한 자식 차례를 본다. 걸리면 보고서를 내보내지 않는다.
  이 검사는 스키마 파일 없이 담당자 PC 에서도 돈다.
- 검증은 세 가지를 다 한다: **모든 워드 부품**의 스키마 검증(개발 쪽은 ISO wml.xsd, 배포본은
  `verify.check_docx`) + LibreOffice 렌더링(쪽 수·빈 쪽·항 시작 쪽) + Word 로 실제 열어 보기.
  **`word/document.xml` 만 검증하면 놓친다** — 두 번의 '읽을 수 없습니다' 가 모두 다른 부품
  (styles.xml, settings.xml)에서 났다. 사선은 LibreOffice 가 그리지 않으므로 XML 로 센다
  (글자와 사선이 겹친 칸은 `기준/Lot No.` 머리 칸만 허용).

## 전년도 결재본과의 관계
- 값의 근거: 배치 크기·포장 단위·시험항목 이름·허용기준 문구·10항 IQ/OQ 값·16항 문안은
  전년도 결재본에서 가져오고, 평가 년도 값(Lot·수율·시험결과·일탈·변경·안정성)은 올해 자료로
  바꾼다(`references/report-format.md`, `house-style.md`, `standard-wording.md`).
- 첨부 Cpk 파일(HLF-QC-126-08/-09)은 전년도 결재본에 딸린 파일을 물려받아 값을 갱신한다.
  전년도 결재본이 없으면(첫해 제품) Cpk 첨부는 만들지 못하고 '문의 목록' 에 남긴다.
- 문서번호 규칙(`PQR{YY}-5-{코드}`)·작성일자·표지 관련 규칙은 **전년도 양식에만** 해당한다.
